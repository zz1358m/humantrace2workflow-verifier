# Stage 03：出报告，对照验收修到通过

本阶段用真实执行结果完成日报、适用周报及交付验收；正常完成或局部阻塞都要走到这里。读 SKILL.md、可用的 references/contracts.md、验收 prompt（或 verifier.yaml），读取 `work/context.json`、`work/queue.csv`、`work/results.json`、`work/reconciliation.json`、`work/execution.md`、原始 input 和 output 后台文件。不依赖其他阶段记忆。缺少补充 references 不豁免交付检查。

先检查是否只完成预检：只有 context/queue/BLOCKED、没有逐单结果，不是合法收工。若授权及输入仍完整，返回 Stage 02 完成遗漏订单后再来；返回前核完整当日日志和通知，避免重放已完成动作。确因不可逆错误/缺证不能执行时，保留原件及缺件事实，仍写实际日报和 DELIVERY 并运行 verifier；REPORT 不用 BLOCKED 替代，漏处理不改名为“今天不动”。

先从后台原件独立复算结果，检查 reconciliation 的来源和差异。若发现业务动作与交接摘要冲突，以原件为事实并记录问题，不改原件，不重放退款或通知。可逆的汇总错误在此修正；危险或不可逆问题按 skill 停下规则交接本人。

还要从 requests/approvals/prev_state 独立重建候选，再看 orders 字段排序、核权限及完整应退额；不能直接接受 queue/results 中的“旧单”标签。对所有日志订单（含队列外）检查动作和通知资格，逐项列出：无来源动作、仍待审批却重复升级、错误退款占额后导致的应退变升级/模板错误。O2/O6 报“额外订单”时先查候选来源；有较早 first_requested_at 不证明检查器漏单。预期额度来自应有队列，实际额度来自日志，两边分别保留；相互自洽的实际 state/REPORT 不能证明 R2/R4 正确。

旧待额度单另核：是否有今日新申请/审批决定，轮到它时应有余额能否覆盖完整应退额；不能把交接中的“额度重置”当作已恢复动作资格。无新事件、权限与签收满足但整单仍不足的旧升级单应只查询、零业务动作及通知，保留 awaiting_budget；足额时则必须接续退款。运行 O8 独立检查这一边界，逐项记录误升级/误通知及原日志行；O2/O6/PR3 与 O8 共同通过才可认为该分支正确，不能靠总体退款金额正确或旧自评 PASS 放行。

按 PR5 核对写前对账确已发生：Stage 02 收工回执/完整日志对应当前日终范围，先核每单及总数，再生成 REPORT；周日先完成当天业务和日报，再汇 WEEK。把现有收工回执及对账依据保留到 output（可用 backend-receipts.jsonl 与 reconciliation.json），不靠文件修改时间或自称“已核对”证明顺序；没有证据就如实记未证实，不补造时间。

不要只核退款合计。逐一核当天五类结果，特别对照旧 need_return 的今日申请、历史通知、新审批和当前签收：无新申请、仍未签收且无新驳回应只查询、零通知，今天结果为不动，后续仍待签收。其实际与预期不一致时，O2/O5/PR3 的 FAIL 是执行错误，不能自评为规则不明而通过。日报保留此单及后续条件；正常不动单写“不动（旧单待签收）”、金额 ¥0.00，不写成重复退款或已结案。首行暂不退数按当天实际 need_return 单数，待签收存量另列；周日行沿用同一当日口径。

仍待权限审批且今天不动的旧升级单写“【待你处理】不动（旧单待审批）”、本日实退 ¥0.00，原因列明待审批额、无新决定、未重发和下一步；与今日升级行一起置顶，但不计入今日升级数。今日升级数仍以实际日志为准；若已错误重复升级，报告保留实际次数并标出错误，不删单、不改成理想的零动作。P1 同时核不动旧单的跟进条件，O7 失败不可自评豁免。

仍待额度且今天合法不动的旧升级单同样置顶标“【待你处理】不动（旧单待额度）”、金额 ¥0.00；原因给完整应退额、轮到时可用额度、未重发和下一步。它仍计入期末 pending，不计入今日升级数；周日报表也沿用实际当日动作与期末存量分开统计。RD1/P1 检查这一交接，O8 的实际错误不因补好报告而消失。

基于核实后的结果写 `output/REPORT.md`；周日再写 `output/WEEK.md`。按自动提供的验收 prompt 决定报告表达，不重述过程、不粘贴工具调用。展示时重新排序，不改执行记录。异常、仍需本人处理和无法确认的数字要让读者一眼定位，不能以“全部完成”覆盖未决项目。

在 skill 目录运行 `python verify.py --input <运行根/input> --output <运行根/output>`。先读输出的 policy，再逐条处理 FAIL；只修可逆产物，在允许轮数内重跑。遇到 TODO，按各自 rubric 核对输入与产出，自评写 `output/judgments.json`（`{"条目ID":{"pass":true/false,"detail":"具体依据与限制"}}`）。无法证实的来源和历史口径如实列未证实，不用空泛“通过”。加入 `--judgments <运行根/output/judgments.json>` 再运行，保存结果为 `output/verification.txt`。

O6 独立核必要文件、队列覆盖、逐单收尾及日报实际总数；O2 的未知规则或 BLOCKED 文案不能掩盖其他单未执行、漏通知或漏日报。即使业务决定暂不能全验，也先从实际记录核 REPORT 的退款数/金额/升级数；保留原有业务 FAIL。不得因没有资金动作就把 R1/R2/R4/R6 当作不适用，最终验收必须实际运行并留存结果。

写 `output/DELIVERY.md`：业务文件链接、最终 verdict、各 TODO 自评结论与依据、仍未证实项、修复轮数、需本人接手事项和范围限制。把 work 中已由工具实际捕获、且评审需要的后台回执/导出证明原样保留到 `output/backend-receipts.jsonl`（确有此物才交，不伪造），让评审仅凭 input/output 也能读取依据。不要把完整日志、命令或验收长表贴入 REPORT/WEEK。存在不可修的失败就交付真实失败，不声称全部通过，不等待在线确认。

PR4 另核实际异常的后续处置：区分“报告写错已按原件修正”和“后台确已多退/误通知”；后者在 DELIVERY 中写清受影响订单、实际金额或模板/次数、停止了哪些自动动作、尚需本人跟进的事项，并保留原始行号/回执。诚实交接不使原业务 FAIL 变为 PASS。

最后写 `work/final.json`：`deliverables`、`verification_file`、`verdict`、`pending_items`、`fix_rounds`、`handoff_required`。完成条件：必要报告齐全，所有 FAIL 已修复重验或明确标为不可逆/缺证，TODO 逐条有诚实结论，后台原件保留完整；只有全部适用硬标准已满足才标完成。
