# 每日退款：先查后动，收工对账

## 何时使用

每天一批，一周七天；已有授权覆盖当天退款、升级及对应通知时执行。仅要求查看或修改报告，不构成资金动作授权。每个会话沿用本 skill 和同一份 verifier 验收 prompt，不凭聊天记忆延续规矩。**默认由当前执行者连续完成 Stage 01→02→03；stage 是工作步骤，不是结束会话或等待另一位执行者的指令。** 只有用户或实际调度明确分派单个阶段时才交接该阶段；完整日批次不能以预检、队列或 BLOCKED.md 代替执行和日报。

## 输入

- 业务日期、`input/requests.csv`（申请 ID、订单、申请时间、原因）。申请条数与去重订单数分别计数。
- `input/approvals.csv`（如有）、昨日收工的 `input/prev_state.json`、以前的日报及周初后台基线（跨周时需要）。第一天可无昨日状态；是否首日由输入明确。
- `input/env.py` 或等价接口及帮助、后台订单现状、最初申请时间、实际退款历史、支付/发货/签收、金额/运费、剩余额度、当日已做动作。
- 当前有效规则。已知未获批超 ¥500.00 需主管批准；扣费前后跨门槛时必须有比较字段依据。不可自行沿用旧 ¥1000.00 权限。

具体字段、检查可见性和交接格式见 [references/contracts.md](references/contracts.md)。路径相对本 SKILL.md 解析。它是补充说明，执行所需核心分支见下文；若运行副本未携带 references，记录缺失并用本页、stage 和当次后端帮助/源码核实协议，继续已明确的业务，不把缺少说明文件等同于缺少退款授权。后端协议改变时调整字段适配，不改变验收标准。

## 产出

`output/journal.jsonl`、`output/state.json` 由后台生成，原样保留。每日 `output/REPORT.md`；周日另有 `output/WEEK.md`。验收结果和 TODO 自评单独放 `output/DELIVERY.md`、`output/judgments.json`，不用技术流水占据业务报告。

阶段通过 `work/` 与 `output/` 保存检查点；恢复或确有分派时也使用这些文件交接。三个阶段分别见下方链接。`work/` 是辅助证据，不替代后台日志；保存检查点后立即进入下一阶段。

## 硬性约束

- 动手前先读昨日状态和审批，把遗留单、获批旧单与新单合队，按**最初**申请时间串行处理。表内行顺序和日报置顶顺序都不是操作顺序。
- **先证明入队来源，再排序，再判动作资格。** 候选来自今日 requests、有效审批，以及历史实际未结的 escalated/need_return；`orders` 是查询目录，`first_requested_at` 只负责排序。只有旧日期、没有今日申请/审批/历史待办记录的订单不自动补办、退款、升级或通知。昨日状态有日期缺口时保留缺证，不把“没查到退款”解释成“从未退款”，也不凭目录补造缺失日待办。
- 每单动作前查后台；不要用买家说已寄回替代 `return_received`，不要把过去发过通知当作已退款。历史已经退钱的单仅查询，不再退款、入库或通知。**列入核查队列不等于今天要做业务动作**；历史仅发过 `need_return`、今天无新申请且仍未签收的旧单，在无新驳回时查询后不动，零通知，继续保留待签收跟进。已签收或有新申请/驳回则重判分支，不能一律跳过旧通知单。
- 买家原因扣有效运费；需退货但未签收时按下述新旧分支处置。首次处理或有新申请/审批决定时，未获批超权限、整单额度不足均整单升级，不拆退，不提交试探性退款。主管批准只解除权限关口，不免除签收和额度关口；旧存量另按不动关口判断。
- **旧升级不是每日重新升级。** 有历史升级记录、今日无新申请/审批决定、当前仍超过审批权限的单，查询后 `untouched`、`carry_status=awaiting_approval`、零业务动作、零通知；保留待主管处理。权限已满足的旧升级单仍按最初申请时间核签收和整单额度：**轮到它时**足额才接续退款；仍不足则 `untouched`、`carry_status=awaiting_budget`、零业务动作、零通知，保留原待办。每日额度重置只是重核的理由，不证明本单已足额，也不授权重复升级。今日新申请或新审批仍重新判分支；不把修复泛化成旧单一律静默。审批金额跨阈值仍需有效比较口径。
- 逐单走完整分支：成功退款→适用入库→`refunded`；升级→`escalated`；首次待退货或今日新申请仍未签收→`need_return`；审批驳回→`rejected`、不退钱；无新申请且仍未签收的旧 `need_return`→只查询、不动。未发货不机械入库。决策表见 [references/contracts.md](references/contracts.md#当日动作与跨日存量)。
- **应通知单**的通知是该单当天最后一个动作，恰好一次；今天不应动的单零通知。发送前核 `notification_required`、模板与完整当日已发次数，不能把“每天跟进”解释成“每天提醒”。恢复执行时把本人和其他执行者已做的动作一并纳入，不能重做。通知后也不再对该单 lookup，收工用批次级 status 和既有记录对账。
- 不修改、重建或删减后台日志和状态来“修正”结果。退款/通知出错不能靠第二次动作抵消。
- 先完成并核对当天后台，再写日报；周日先做完当天，才汇总本周。周末 pending 按后台定义的当前存量核对，不加总每日升级单数；待签收另列清楚，不能隐去。

## 当前原因与金额分支

以下将原因适配明确写到执行入口，后端事实仍须逐单 lookup 确认。先核入队来源，再判断历史已退款/结案、今日驳回、旧升级是否仍待审批、已发货未签收等分支，最后计算可退款单的金额：

- 明确的质量问题、发错货、**因未发货而取消**按订单金额全额核定；不能仅凭取消时说“不要了”就泛化为买家原因。未发货无需等退货签收、不入库，非零 shipping_fee 本身不改变原因分类。
- 明确买家原因且已发货，完整应退額为 amount 减 shipping_fee；确为买家原因但未发货、且有非零运费时，运费是否适用仍需当次有效规则，不能套用未发货取消分支。原因矛盾或陌生时只标相关单待核，不从旧日报创造规则。
- 完整应退额及审批比较字段明确后，先查权限再查**轮到本单时**的剩余额度；首次处理或有今日新申请/审批决定的单，未批准超权限或整单额度不足→升级并发 escalated，然后继续下一单；升级不占退款额度。批准不免除签收和足额条件。
- 上述升级不覆盖无新申请/审批的旧待审批、旧待额度不动关口。旧待额度单只查不动也不占额度，继续按序核下一单，不把尚未满足的金额预留为已退。独立计算“仅合法队列应退款项占用的预期额度”，并与实际后台余额比对；若未经资格确认的退款已挤占额度，记录执行错误并停止受影响资金动作，不能用错误后的实际余额把后续应退单改判为升级或合法不动。
- 扣费前后跨 ¥500.00 且未批准时仍需有效 gross/net 比较字段；本次输入没有触发的未知边界不阻塞其他分支。不得为了验收自行编造 refund_rules.json。

## 必须停下的情况

停止的是受影响单的危险动作，继续能独立完成的订单，并进入 Stage 03 交付实际结果和未完成项；本任务无人值守，不等待聊天确认。一个较晚订单待核，不能挡住它之前已明确的单。若较早单的未知决定会影响后续额度或实际动作顺序，保留该依赖并暂停受影响的后续动作，不让晚申请单先占额度；不相关的取数、对账和报告继续。BLOCKED.md 只能补充原因，不能取代 REPORT.md 或跳过 verifier。

- 权限/额度不足：按新处理/旧存量关口决定首次升级或只查不动并继续队列，不把正常业务待办当成整批阻塞。
- 实际多退、支付拒绝、重复退款/通知、不可撤销顺序错误：冻结该单的自动补救，保留原记录，交本人跟进；若额度或日志可信度受影响，停止后续资金动作。
- 关键字段、有效规则、跨门槛口径、未支付订单处置不明，或后台状态与日志冲突：记录缺失依据，停止相关资金及结果通知；不得编造审批或默认签收。
- 来源缺少独立签名、非周日缺周初基线等，只影响相应证据结论；不能把这些验证限制升级为明确已授权的当日业务全部停止。
- 同日已有通知后又出现新状态、并发操作者仍在修改、调用超时不知成功与否：先从批次状态/日志确认实际结果，不能盲重试。无法确认就留待本人处理。
- 验收 policy 的可逆修复轮数耗尽后仍有失败：如实交付失败与影响，不再试资金操作。默认两轮是继承的暂定机器策略，不是本人规定的退款重试次数。

## 步骤

1. **取数、合队、设关口** — [stages/01-reconcile.md](stages/01-reconcile.md)。输入当天表、昨日状态、审批和后端协议，输出 `work/context.json`、`work/queue.csv`、`work/preflight.md`。交接候选来源、新申请、新审批、历史升级/通知、签收与重开触发条件，区分待查询与待动作；不在这一阶段发款或通知，保存后立即继续 Stage 02。
2. **逐单执行并核数** — [stages/02-process.md](stages/02-process.md)。逐单查询，先判当天动作及是否应通知，再核应退额/审批/足额条件；通知前复核，完整收尾后才推进下一单。输出后台原件、`work/results.json`、`work/reconciliation.json`、`work/execution.md`；任何调用结果不明都在本步止住，不留给报告阶段猜。
3. **写结果、审查并修正** — [stages/03-deliver.md](stages/03-deliver.md)。从输入重建资格及五类当日结果，核预期额度与实际动作，用实际对账结果生成报告。日报首行给申请数、退款数/合计、升级数、当日暂不退数；待签收/待审批/待额度存量另列，有来源旧单今日不动仍保留在四列表，今日升级和仍待本人审批或安排额度的行置顶标记。周报首行给周退款数/合计和周末待办，下面每天一行。不写寒暄或执行流水。运行 verifier，修正可逆错误，交接全部产物和未决依据。

## 交付前验收

无论正常完成、局部阻塞或本批无资金动作，最终都运行 `python verify.py --input <输入目录> --output <产出目录>`；不能因“只完成第一阶段”绕过。O6 独立检查必要文件、逐单收尾和日报实际总数，BLOCKED/预检不豁免失败。FAIL 的修掉重跑，TODO 的条目按 rubric 逐条自评并把结论写进交付说明；按输出里的 `policy` 行事（查多深、最多修几轮、什么情况停下问人）。

O7 从原输入和完整日志独立查动作资格，包括未进入预期队列的动作；O8 不复用 O2 的决定，从原输入按序分配应有额度，检查无新申请/审批且轮到时仍缺额度的旧升级单已查询、零业务动作及通知；O2/PR3 查按正确队列推导的结果与通知。队列范围 FAIL 不能解释成“检查器漏了目录订单”，也不能以实际余额自洽代替 R2 的应有决定；对照原输入定位错入队、重复升级和额度连锁差异。

从 skill 目录运行上述命令，或用 `python <skill目录>/verify.py`。policy 继承全量核查、执行前后都查、以证据验证、可逆错误至多修两轮；必须转人工的情况记在 `output/DELIVERY.md`，无人值守时停止对应危险动作并交接，不阻塞等待。将自评保存为 `output/judgments.json` 后加 `--judgments <该文件>` 再验。存在 TODO 的机器 ACCEPT 只表示已决定条目通过，不代表完整交付通过；未证实的来源或数据口径必须保留限制。

可逆修复只改报告、计算和未执行计划。若是整段 Stage 02 从未执行，在确认完整当日记录和原授权后继续该阶段，属于完成原任务；已有退款/通知不重放，也不越过停下关口为失败单自动补救。不可逆错误不得重放后端动作或伪造记录来通过验收。历史 cases 是局部报告回放，没有提供后台全流程的正确性背书。
