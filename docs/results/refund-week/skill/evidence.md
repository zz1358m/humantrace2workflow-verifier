# 验收证据链与边界

本任务采用目的→输入→约束→检查点→结果的组织方式，来自 profile/profile.md 中短指令、沿用旧规矩、先核旧状态/审批、逐单执行、写前对账的工作节奏。已核读指定全部日期的 events/signals，排除了无关生活和他人做法。request.md 的 R1–R7 是 stated；signal 的类型本身不等于标准，关键是本人实际说了什么及是否有产物支持。

## 来源与可复核性

有实物的只有 workdir/0616 与 workdir/0621；这批 traces 没有 shots/blobs，也没有可用 rejected_sha/kept_sha 对。四个 case 原样复制 workdir 文件，元数据记原路径/SHA256；日报初稿按 REPORT.md 名回放，周报初稿按 WEEK.md 名回放，没有改正文。input/replay.json 是编译器标注的回放范围，不冒充当时输入。

案例是两个局部报告版本对，不是四个完整日批次。0616 输入有原始 requests 和 journal，缺 orders/state/prev_state；0621 只有当天实际请求原文，缺逐日后台记录。缺文件不补造。所有片段限定条件直接写入检查协议，真实 env/orders/prev_state 输入不允许启用片段模式。完整运行缺产物会失败；片段的未适用检查会说明“未验证”，不冒充通过全流程。

当前后端协议取自现有运行输入的 env.py/orders/requests 等，仅用于实现读取与状态变更语义。检查脚本没有任何历史订单 ID、日期、退款总数或金标准产出常量；没有读取 runs/*/output，也不在脚本中读取 case 输出。原始历史申请/通知/退款的真假从输入与输出可用原件核对，不依据本人当时打开过什么页面。

## O1：原件齐全、状态延续及重放一致

- **证据**：request:R1 直接要求 journal/state 由后台生成，request:R7 要求周报；2026-06-17 09:30:00 明说先看 prev_state。
- **推出**：完整运行必须保存可解析原件，所有昨日历史经当天动作延续；用输入状态和日志按后台协议重放，比只看报告总数更能发现漏记录或清空历史。
- **其他解释**：最终 state 数字正确可能来自手工编写，不足以证明动作真的执行。因此 O1 只声称结构和重放一致，来源另交 O4，不能把重放通过解释为独立认证。
- **边界**：后台协议改变须调整适配；不得通过修改业务门槛或删除历史字段迁就 workflow。历史片段不执行完整文件要求，并明示缺证。

## O2：逐单业务决定及应退额

- **证据**：request:R2；2026-06-10:S004/S005 纠正不扣运费，说明查订单再决定；2026-06-12:S001/S002 拒绝未批超 ¥500 退款，S004 规定未签收发 need_return，S005 规定额度不足整单升级；2026-06-17:S002 规定获批旧单当日接续；2026-06-18:S001/S002 区别历史退款与历史通知，S003 规定驳回通知。
- **推出**：从输入重建新旧队列，以后台字段和实际历史判分支；审批只解除权限限制，不免除签收/当日整单额度。未变化的旧 need_return 仍核状态，不因昨天已通知而重发；新的再次申请则按当天输入处理。day-2 的 R2/R4 反馈进一步明确：无新申请且仍未签收、无新驳回时，当日结果是 untouched（不动），后续存量是 awaiting_return，不能仍以 need_return 当作当日结果。
- **其他解释**：可以把“处理过”当成重复，但本人 S001 明确否定；可以仅看新表，但 S002 明确否定；可以把所有高额订单永远升级，但已批准旧单必须接续。因此这些简化均排除。
- **边界**：已发货买家原因扣运费的证据最强。未发货且确为买家原因是否也扣运费、未支付订单处置、陌生原因分类、金额扣费跨阈值均无充分轨迹证据；遇到此类输入要求有效规则或 FAIL/停该单，不臆造标准。已知“质量问题”和“因未发货取消”走全额的支持比扣运费纠正弱，保留在可审查的适配分支中，confidence 0.96 而非 1.00。
- **实现**：应退额用 Decimal；顺序分配每日额度，不把所有订单均按开工额度判断。申请同时间的先后没有规定，校验实际采取的任一种同时间顺序，不硬加订单号偏好。

## O3：不拒付、不拆退、不重退

- **证据**：request:R5；2026-06-12:S005 的“不要拆开退”及 S006 叫停；2026-06-18:S002 的“退过的一律不动”。
- **推出**：既看当日日志所有退款调用，也看昨日 refunds；失败后又成功、拆为两次凑出正确总额仍不合格。
- **其他解释**：只看净退款额可能相同，但本人明确在乎一次完整退和系统拒绝，所以不能只验末态总和。
- **边界**：6/12 agent 声称先退部分、后来整单升级，没有完整日志，不据此造一个真实资金 case。测试中的失败日志是明确标注的合成回归输入，非历史 case。

## O4：诚实说明来源与累计可证范围

- **证据**：request:R1 明说“由后台生成，不是手写”；request:R7 及 2026-06-21:S001 要后台累计一致；2026-06-16:S003 要写前先对后台。
- **推出**：文件存在不等于来源已证实，表内加总不等于后台对账；需要将不能验证的部分保留为未证实。
- **其他解释**：本人说“行”也许意味着完成全面审计。但 6/21 17:10 的 status 只有命令、无返回值，不能推出此事；普通 JSON 更无法排除逐字手工伪造。
- **边界/不确定性**：这是最难自动判定的一条。验收仅可读输入与输出，无法认证完全无签名的生成来源；judge 查看现有回执/协议及限制，不要求获取执行时不可见的个人浏览记录。无签名时可以报告一致性通过，但绝不声称独立认证；未解决的真实性不能靠自评文案强行通过。confidence 0.85 是评审可判定性限制，不降低 R1 本身的强度。

## PR1：先查后动

- **证据**：request:R3；2026-06-10:S005 明说“后面的单动手之前都先查订单”。2026-06-12:S003 得知字段后 S004 才明确挡住退款。
- **推出**：每单首次非查询动作前必须有当天 lookup。状态文件读取不能冒充后端查询；昨日查询不满足当天前置。
- **其他解释**：要求每个单独动作前都再查一次会导致通知后查询，且本人实例是查询→退款→入库→通知。故每单必要前置查询即可，不机械要求每个操作前重复 lookup。

## PR2：合队后的实际动作顺序

- **证据**：2026-06-10:S003 否定 CSV 行顺序；2026-06-17:S001 说明旧单晚处理导致额度被抢，S002/S003 强调最早获批单当天接续；2026-06-09 09:11:10–09:12:10 本人逐单收尾后再处理下一单。
- **推出**：实际非查询动作按最初申请时间推进，完整当前单后再下一单。批量预先读取字段可以，不能并发抢用额度。
- **其他解释**：日报待办置顶不意味着先操作升级单。6/16 最终表把 B2002 放前，而 journal 顺序仍是 B2001→B2002→B2003，排除“报告顺序等于操作顺序”。
- **边界**：允许同申请时刻任意稳定先后；没有规定秒精度或同时间按订单号。串行标准限本退款流程，不外推反对所有并行工作。

## PR3：逐单收尾、入库和通知

- **证据**：request:R4；2026-06-10:S001 先通知后退款被叫停；2026-06-09 09:12:10/09:13:45 分别为 refunded/escalated；2026-06-12:S004 need_return；2026-06-18:S003 rejected；2026-06-18 09:06:30 成功退款后的入库。
- **推出**：通知最后且一次，退款后适用入库，模板与当日结果匹配；跨会话恢复要合看完整日记录。
- **其他解释**：通知只是 agent 最后动作就行，但 request 指该单当天最后动作，故本人/其他执行者已做的动作也算。日志记录的通知后 lookup 也会被判错，批次 status 则无逐单动作，不算。
- **边界**：未发货单不入库，不能把已发货退回商品的实例推广成每单都入库。6/18 驳回通知的 shell 和 agent 回复可能重叠，不能断言有两次成功；不据它建重复通知历史 case。规则仍由 R4 支持。

## RD1：日报具体格式、口径与对账

- **证据**：request:R6；2026-06-12:S007 五项数字、S008 四列表和金额格式、S009 待本人处理行置顶、S010 接受；2026-06-16:S001 否定寒暄/过程/命令，S003 要写前对后台。
- **推出**：首行申请条数、退款单数/合计、升级单数、暂不退单数；表里一订单一行，旧单不可遗漏。升级金额不混入实际退款额；数字由输入和当日日志推导。暂不退按当日实际 need_return 去重单数统计，未变化的待签收存量另列，周日行同口径；动作本身是否应发生仍受 O2/O5/PR3 约束。
- **其他解释**：6/16 S002 可能证明实际多退、实际顺序错。但 journal 与 S003 表明后台实际是 ¥80.00 和正确先后，故 reject case 是报告返工，不构造错误操作。
- **格式范围**：账款数值强制 ¥ 加两位小数。保留版原因中写“超过 ¥500 需主管审批”，它是规则阈值引用而非账款，脚本不把它当成金额栏格式错误；新 workflow 统一写 ¥500.00。这一窄区分来自本人留下的文本，不放宽真正金额数字。
- **继承关系**：通用结论先行/例外优先/不写流水分别继承 RP1/RP4/RP5；RD1 不再另立通用风格规则，而是把这些要求落成这个任务的具体字段检查。脚本检测常见寒暄/命令，隐晦冗长叙述仍由继承 RP5 与 P1 评审。

## RW1：周报是本周增量与周末存量

- **证据**：request:R7；2026-06-21:S001 要首行本周退款数、金额和未完成数，下方每天一行，数字与后台累计相符；S002 接受修订。
- **推出**：周一到周日七行，首行与行总额自洽，还必须核后台本周增量及周日末 pending。不能用全历史累计替代本周，不能相加每日升级数当未完成数。
- **其他解释**：只查七行加法即可，但明确“后台累计”排除。6/21 快照自洽但缺 backend，case 仅验证结构/算术，不能反推其金额是真实后台总量。
- **边界**：当前 env.pending 是未退款且未驳回的升级单集合，不自动含 need_return；按照真实后端口径报告该数字，并将待签收另列，防止“仍待处理”让人误解。跨周缺基线、旧日报无日期时不猜；未知日期不会被强行套到周一，O4 明确审查该缺口。confidence 0.98 反映快照不能认证历史累计。

## P1：例外原因可执行

- **证据**：2026-06-12:S008 要“原因”、S009 说“我只先看这几行”；2026-06-17:S002 对获批漏退追问；2026-06-18:S001 区分过去通知和实际退款、S003 强调驳回不能让买家干等。
- **推出**：不是只标“异常”，要指出阻塞类型和下一步；否则本人仍要重查后台。rubric 给具体正反例，不规定长度或用固定套话。
- **其他解释**：可以要求每个异常详细长篇解释，但本人反复拒绝过程叙述，所以只保留做决定所需的原因。
- **不确定性**：是否已经“足够清楚”依赖语义，confidence 0.88、非 hard；不能由脚本搜索关键词就证明。没有证据支持更细的词汇或固定句式偏好。
